# Этап: PostgreSQL для orders-service

> Это разбор первого этапа. Платежи уже тоже переведены в PostgreSQL, а временные ограничения `Map` сняты во [втором этапе](02-postgresql-payments.md). Ниже сохранено описание промежуточной архитектуры для последовательного изучения. Текущие команды `db:up` и `db:migrate` обслуживают обе базы.

## Что изменилось

Раньше OrdersService хранил заказы в `Map`. Теперь он делегирует хранение OrdersRepository, а тот обращается к PostgreSQL через TypeORM:

```text
HTTP → Controller → OrdersService → OrdersRepository → PostgreSQL
                          │
                          └── HTTP → payments-service
```

TypeORM — ORM: библиотека, которая связывает TypeScript-классы с таблицами и помогает выполнять запросы. Она не отменяет SQL, ограничения и транзакции. В первой миграции SQL написан явно, чтобы структура базы не была скрыта за декораторами.

Payments-service не изменён: у него пока свой Map. У него нет подключения или доступа к таблицам заказов.

## Запуск

Из корня репозитория:

```bash
npm install
npm run db:up
npm run db:migrate
npm run dev
```

`compose.yaml` запускает только инфраструктуру, а не Nest-приложения. PostgreSQL слушает внутри контейнера порт 5432, с компьютера — `127.0.0.1:15432`. Порт привязан только к loopback.

Healthcheck проверяет готовность PostgreSQL. `docker compose up --wait` дожидается её перед возвратом управления. Именованный volume `orders-data` сохраняет данные независимо от остановки контейнера.

`infra/postgres/init-orders.sql` создаёт базу `orders` и обычную роль `orders`, без прав суперпользователя. Этот init-скрипт выполняется только при первом создании хранилища. Это не замена миграциям и не механизм обновления существующего volume.

Локальный URL подключения:

```text
postgresql://orders:orders_local@127.0.0.1:15432/orders
```

Его можно переопределить через `DATABASE_URL` в `apps/orders-service/.env`. Настоящие пароли нельзя сохранять в Git; приведённые реквизиты предназначены только для этого локального стенда.

## Таблицы

```text
orders                       order_items
──────────────────────       ──────────────────────
id UUID PK              ┌─── order_id UUID FK
amount INTEGER          │    id UUID PK
currency VARCHAR        │    product_id VARCHAR
status VARCHAR          │    product_name VARCHAR
payment_ids UUID[]      │    unit_price INTEGER
created_at TIMESTAMPTZ  │    quantity INTEGER
         │              │
         └──────────────┘
```

### orders — заказ как целое

- `id` — первичный ключ, UUID генерируется приложением.
- `amount` — общая сумма в копейках, строго положительное целое число.
- `currency` — пока только `RUB`.
- `status` — `pending` или `paid`.
- `payment_ids` — ID связанных удалённых платежей.
- `created_at` — момент создания с часовым поясом, выставляется PostgreSQL.

`payment_ids` не имеет внешнего ключа на таблицу платежей: такой таблицы в этой базе нет и не должно быть. Это ссылки на ресурс другого сервиса, а не локальная реляционная связь. Массив пока достаточен для учебного сценария; отдельную модель связей можно добавить позже.

### order_items — позиции заказа

Позиция ссылается на заказ через `order_id`. PostgreSQL не разрешает создать позицию несуществующего заказа — это внешний ключ, FK.

В позиции сохраняются **название и цена на момент заказа**. Если каталог позже изменится, старый заказ не должен пересчитываться по новым ценам.

Сейчас HTTP API принимает только один товар. Внутри он сохраняется как одна позиция; добавление корзины и изменения HTTP-контракта в этот этап не входят. Репозиторий преобразует позицию обратно в прежние поля ответа `productId`, `productName`, `quantity`, поэтому клиент продолжает работать без изменений.

`ON DELETE CASCADE` означает: при удалении заказа его позиции тоже удалятся. HTTP-удаление заказов сейчас не реализовано.

## DTO и Entity — не одно и то же

| Тип               | Назначение                          | Пример                             |
| ----------------- | ----------------------------------- | ---------------------------------- |
| DTO               | Проверить входящий HTTP-запрос      | productId и quantity от клиента    |
| Entity            | Описать соответствие класса таблице | OrderEntity и OrderItemEntity      |
| HTTP-модель Order | Вернуть стабильный ответ клиенту    | ISO-строка createdAt и поля товара |

В Entity дата имеет тип `Date`, в JSON-ответе она становится ISO-строкой. Реляционные `items` не обязательно должны целиком попадать во внешний API. Преобразование сосредоточено в `OrdersRepository.toOrder`.

Проверки DTO улучшают ответ API. Ограничения базы защищают данные даже при записи через другой код или напрямую через SQL. Поэтому положительная сумма и допустимое количество проверяются не только на входе HTTP.

Пока общая сумма вычисляется сервисом как `unitPrice * quantity`. База не проверяет равенство `orders.amount` сумме всех позиций: межтабличное правило остаётся ответственностью кода создания заказа.

## Миграция

Файл: `apps/orders-service/src/database/migrations/1794355200000-CreateOrders.ts`.

- `up()` создаёт таблицы, ограничения и индексы.
- `down()` удаляет сначала позиции, затем заказы.
- TypeORM хранит историю выполненных миграций в таблице `migrations`.
- Повторный `npm run db:migrate` не выполняет уже применённую миграцию повторно.
- `npm run db:migrations` показывает статус миграций.

При запуске Nest миграции не применяются автоматически: `migrationsRun: false`. Схема также не синхронизируется с Entity автоматически: `synchronize: false`. Поэтому после создания базы необходимо отдельно выполнить `npm run db:migrate`.

Команда сначала компилирует TypeScript, затем запускает CLI на `dist/database/data-source.js`. CLI и Nest используют общую функцию `databaseOptions`, чтобы настройки подключения и список Entity не расходились.

Изменения схемы в дальнейшем оформляются **новой миграцией**, а не исправлением уже применённой. Откат первой миграции уничтожает таблицы с заказами; на рабочей dev-базе без необходимости его не запускаем. В интеграционных тестах `down()` проверяется на одноразовой пустой базе.

## Транзакция создания заказа

Нельзя допустить ситуацию «заказ сохранился, а позиция — нет». Поэтому создание обёрнуто в `manager.transaction`:

```text
BEGIN
  INSERT INTO orders ...
  INSERT INTO order_items ...
COMMIT
```

Если вставка позиции нарушает ограничение, вместо COMMIT происходит ROLLBACK: заказ тоже не сохраняется. Внутри callback используется только переданный `manager`, чтобы обе записи выполнялись в одной транзакции. Cascade insert здесь помогает ORM сохранить связанную позицию, но сам по себе не заменяет границу транзакции.

HTTP-запрос к payments-service выполняется **за пределами** этой транзакции. Локальная транзакция PostgreSQL не может атомарно закоммитить данные другого сервиса. Если платёж создан, а запись его ID в orders-service не удалась, нужна отдельная стратегия восстановления; outbox и сверка будут позже.

## Обновления после оплаты

Связанный payment ID добавляется атомарным SQL UPDATE с проверкой отсутствия в массиве. Это безопаснее, чем прочитать массив, поменять в JavaScript и целиком перезаписать: такой подход мог бы потерять параллельное обновление.

Успех оплаты меняет статус заказа в PostgreSQL. Отказ не меняет оплаченный заказ обратно на pending. Повтор уведомления идемпотентен по результату: состояние заказа остаётся тем же.

**Важно:** кеш ключей идемпотентности OrdersService пока остаётся в памяти. База заказов сохраняет заказ и payment IDs, но не обещает долговечную идемпотентность всей оплаты. Её разберём на следующем этапе с базой платежей.

## Посмотреть данные руками

```bash
docker compose exec orders-db psql -U orders -d orders
```

Внутри psql:

```sql
\dt
\d orders
\d order_items

SELECT id, amount, currency, status, payment_ids, created_at
FROM orders
ORDER BY created_at DESC;

SELECT o.id, o.amount, i.product_name, i.unit_price, i.quantity
FROM orders AS o
JOIN order_items AS i ON i.order_id = o.id
ORDER BY o.created_at DESC;

SELECT * FROM migrations;
```

Выход из psql — `\q`.

## Эксперимент с перезапуском

Для удобства запусти каждое приложение в отдельном терминале:

```bash
npm run dev -w @lab/orders-service
npm run dev -w @lab/payments-service
npm run dev -w @lab/client
```

1. Создай заказ через клиент и запомни его ID.
2. Останови только orders-service и запусти снова.
3. Обнови страницу: заказ, количество и сумма останутся.
4. Оплати заказ, перезапусти только orders-service ещё раз: статус `paid` и ID платежа тоже сохранятся.
5. Сравни данные интерфейса с SQL-запросом.

Не перезапускай payments-service в этом эксперименте: его платежи пока в памяти и будут потеряны. База заказов не умеет восстановить чужие платёжные записи по одному ID.

## Автоматические проверки

```bash
npm test
```

Тестовая PostgreSQL работает в отдельном контейнере на 15433. На каждый запуск создаётся своя база со случайным именем. В ней применяются миграции, проверяется откат, затем запускаются реальные Nest-процессы. В конце удаляется только созданная тестом база. Dev-база не используется.

Дополнительно к HTTP-сценариям проверяются:

- сохранение заказа, позиций, статуса и payment IDs после реального перезапуска процесса;
- повтор уведомления после перезапуска orders-service;
- снимок товара и суммы в таблицах;
- полный откат заказа при ошибке позиции;
- запрет позиции для несуществующего заказа.

Тестовая роль специально имеет административные права для создания временных баз. В dev-сервисе применяется обычная роль `orders`; переносить тестовые права на приложение не нужно.

Тестовый контейнер использует tmpfs, не долговечный volume: после остановки его данные не предназначены для сохранения. `npm run db:test:down` останавливает его. Dev-volume эта команда не затрагивает.

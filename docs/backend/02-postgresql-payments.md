# Этап 2: платежи, долговечная идемпотентность и конкурентные запросы

## Цель

Сохранить платежи и ключи так, чтобы перезапуск Node.js не создавал новую попытку вместо прежней. Проверить не только последовательные запросы, но и несколько процессов, одновременно работающих с одной базой.

```text
orders-service  ─────── HTTP ────── payments-service
      │                                   │
      ▼                                   ▼
  orders DB                           payments DB
  порт 15432                          порт 15434
```

Каждый сервис имеет собственный PostgreSQL-контейнер, роль и volume. FK между базами нет. В платежах `order_id` — идентификатор внешнего ресурса, а не разрешение читать таблицу orders.

## Запуск поверх первого этапа

```bash
npm install
npm run db:up
npm run db:migrate
npm run dev
```

Команды запуска и миграций теперь обслуживают оба сервиса. Старый volume заказов не удаляется. Миграции, уже применённые в orders-service, повторно не выполняются.

Сервис платежей подключается через `DATABASE_URL` из своего `.env`; значение по умолчанию:

```text
postgresql://payments:payments_local@127.0.0.1:15434/payments
```

`infra/postgres/init-payments.sql` создаёт обычную роль приложения и её базу при первом запуске volume. Инициализация и миграции — разные механизмы. `synchronize` и автоматическое выполнение миграций при старте Nest отключены.

Утраченные до этого этапа in-memory платежи мигрировать невозможно. Существующие заказы сохраняются, но старые ID могут ссылаться на уже потерянные записи. Мы не выдумываем историю оплаты и не сбрасываем данные. Новые эксперименты лучше делать на новых заказах; старый оплаченный заказ не разрешает создать новый платёж.

## Одна таблица: payments

Основные поля:

| Поле                     | Смысл                                                    |
| ------------------------ | -------------------------------------------------------- |
| id                       | Идентификатор попытки оплаты                             |
| order_id                 | Заказ, которому принадлежит попытка                      |
| idempotency_key          | Ключ исходного запроса                                   |
| amount, currency, method | Данные попытки, которые нельзя менять повторным запросом |
| provider                 | Пока только mock                                         |
| status                   | pending, succeeded или failed                            |
| notification_status      | not_sent, delivered или failed                           |
| notification_attempts    | Сколько попыток уведомления начато                       |
| created_at               | Время создания в PostgreSQL                              |

Ключ хранится **в той же строке, что и платёж**. Это проще отдельной таблицы ключей и не оставляет окно «платёж сохранился, ключ забыли». Одна SQL-вставка уже атомарна: дополнительная ручная транзакция вокруг одного INSERT не нужна.

В HTTP-ответ ключ не возвращается. Сервис сравнивает сумму, валюту и метод из повтора с сохранёнными значениями. Отдельный fingerprint не требуется, пока эти поля доступны непосредственно в строке. Если данные не совпали, возвращается `409 Conflict`.

Ключ действует в пределах заказа: `(order_id, idempotency_key)`. Разные заказы могут использовать одинаковую строку ключа. Отказ не освобождает старый ключ и не удаляет запись: повтор возвращает старую неуспешную попытку. Новая попытка требует нового ключа.

## Два независимых ограничения

### 1. Одна запись на ключ

```sql
UNIQUE (order_id, idempotency_key)
```

Проверка `SELECT`, затем `INSERT` в JavaScript не даёт такой гарантии. Два процесса могут одновременно увидеть отсутствие записи и оба начать вставку. Уникальность должна обеспечиваться PostgreSQL.

### 2. Один незавершённый или успешный платёж на заказ

```sql
CREATE UNIQUE INDEX payments_one_active_per_order
ON payments(order_id)
WHERE status IN ('pending', 'succeeded');
```

Это **частичный уникальный индекс**: он учитывает только выбранные строки. Он не позволяет обойти защиту от двойной оплаты, отправив другой ключ. При этом неуспешные попытки остаются в истории и не мешают новой попытке.

Эта модель специально ограничивает один заказ одной полной успешной оплатой. Частичные платежи, возвраты и дополнительные списания требуют другой модели и сейчас не поддерживаются.

## Алгоритм создания

В `PaymentsRepository.create`:

1. Выполняется `INSERT ... ON CONFLICT DO NOTHING`.
2. Делается отдельный SELECT по заказу и ключу.
3. Если запись есть, проверяются сумма, валюта и метод и возвращается её актуальное состояние.
4. Если записи с таким ключом нет, вставку заблокировала другая активная попытка — возвращается `409`.

В TypeORM вставку с `ON CONFLICT DO NOTHING` задаёт `.orIgnore()`. В PostgreSQL она подавляет конфликты уникальности, а не CHECK, NOT NULL и прочие ошибки входных данных.

Отдельный SELECT важен: при READ COMMITTED конфликт вставки может возникнуть из-за параллельной транзакции, строки которой не было в снимке исходного INSERT. Следующий запрос получает новый снимок и видит уже зафиксированную запись. Тест запускает две настоящие реплики платежей, чтобы проверка не зависела от однопоточного JavaScript.

## Почему в orders-service больше нет Map

Раньше локальный Map запоминал ключ и Promise. После рестарта он исчезал, а разные процессы не разделяли его содержимое.

Теперь orders-service передаёт исходный ключ владельцу платежей. Для неоплаченного заказа — через `POST /payments`. Для оплаченного — через защищённый токеном `POST /payments/lookup`, который только ищет существующую запись и никогда не вставляет новую.

Последний случай важен: если старый заказ уже оплачен, но его платёж был потерян на первом этапе, нельзя разрешать создание новой попытки. Известный ключ возвращает прежний платёж; неизвестный для оплаченного заказа превращается в `409`.

Внутренний поиск принимает те же данные, что создание; это позволяет проверить не только ключ, но и неизменность параметров. Тело запроса выбрано, чтобы не размещать ключ в URL. Внутренний endpoint требует `x-internal-token`; клиент напрямую его не вызывает.

После ответа payments-service orders-service одним SQL UPDATE сохраняет ID и, при успехе, статус paid. Повтор не добавляет второй ID. Если ответ потерялся между сохранением платежа и записью связи, повтор с исходным ключом получает тот же платёж и восстанавливает локальную запись. Если потеряно уведомление об успехе, такой повтор также восстанавливает статус заказа.

Это **не распределённая транзакция** и не фоновое восстановление: повтор нужно реально выполнить. Автоматическая сверка и outbox появятся позже.

## Финализация платежа: транзакция и блокировка строки

Два уведомления могут прийти одновременно, в том числе с разными результатами. `PaymentsRepository.recordResult`:

1. Открывает локальную транзакцию.
2. Читает платёж с `pessimistic_write` — в PostgreSQL это SELECT FOR UPDATE.
3. Проверяет переход: pending → succeeded/failed либо повтор того же финального состояния.
4. Сохраняет статус и увеличивает счётчик попыток уведомления.
5. Коммитит транзакцию.

Второй конкурентный обработчик ждёт освобождения строки, затем видит уже обновлённый статус. Противоречащий результат отклоняется, а повтор такого же разрешается. Проверка переходов реализована в репозитории, не SQL-триггером: прямой административный UPDATE всё ещё может нарушить бизнес-правила.

**HTTP выполняется только после коммита**, без удержания блокировки. Это не только уменьшает время блокировки: orders-service при обработке уведомления сам читает платёж через HTTP. Если держать блокировку во время вызова и требовать её с другой стороны, можно получить зависание или дедлок.

## Доставка — отдельный факт

Результат платежа не отменяется при недоступности orders-service. После сетевого вызова отдельно сохраняется результат доставки.

- `not_sent` — подтверждённого результата доставки пока нет.
- `failed` — доставка не удалась и ещё ни одна не была подтверждена.
- `delivered` — хотя бы одна доставка подтверждена.

Успех доставки не понижается до failed из-за ошибки позднего или параллельного повтора. Это реализовано условным UPDATE в `recordDelivery`, а не перезаписью всего объекта из памяти.

Счётчик означает **начатые**, а не гарантированно завершённые HTTP-попытки. Если процесс упал между коммитом и HTTP-вызовом, счётчик уже увеличен. Если orders-service обработал запрос, но ответ потерялся, доставка может быть отмечена как failed: подтверждения у отправителя нет, хотя получатель изменил заказ. Поэтому повторная обработка у получателя должна быть безопасной.

При падении между оплатой и отправкой результат уже долговечен, но сам собой не будет доставлен. Кнопка «Повторить уведомление» работает и после перезапуска. Периодический worker, брокер и transactional outbox в этот этап не входят.

```

SELECT id, order_id, idempotency_key, amount, method, status,
       notification_status, notification_attempts, created_at

ORDER BY created_at DESC;

SELECT indexname, indexdef

```

Выход: `\q`. Настоящие ключи и платёжные данные в production не следует бездумно выводить в логи или общедоступные панели.

## Что проверить самому

1. Создай заказ и платёж через интерфейс.
2. Перезапусти оба бэкенда, обнови страницу: заказ и платёж останутся.
3. Подтверди оплату, снова перезапусти оба сервиса: статусы сохранятся.
4. Повтори уведомление и посмотри счётчик в таблице.
5. Создай новый заказ, останови только orders-service, подтверди платёж. Увидишь сохранённый успех платежа и ошибку доставки. Запусти заказы и повтори уведомление.

Для точной проверки идемпотентности после рестарта нужен исходный ключ. Клиент сейчас хранит его только в памяти страницы; обычный перезапуск серверов его не стирает, но перезагрузка страницы стирает. Ключ не является секретом аутентификации и не заменяет авторизацию.

## Тесты и границы гарантии

`npm test` использует отдельные PostgreSQL на 15433 и 15435. Создаёт две одноразовые базы, проверяет применение и откат миграций, запускает сервисы на 3101/3102 и дополнительные реплики на 3103/3104. Dev-базы не очищаются.

Проверяются:

- повтор исходного ключа для pending и succeeded после рестарта обоих сервисов;
- неизменность суммы/метода и конфликт нового ключа у оплаченного заказа;
- одна запись при параллельных запросах в две реплики;
- история отказов и область действия ключа;
- гонка противоположных результатов и точный счётчик повторов;
- сохранение ошибки доставки и ручное восстановление;
- восстановление связи, если payments-service успел сохранить запись, а заказы ещё нет;
- защита старого оплаченного заказа без записи платежа;
- ограничения даже при записи напрямую через SQL.

Гарантия относится к **записям нашего фиктивного провайдера**. Настоящий внешний вызов нельзя просто поставить перед INSERT и считать защищённым этим индексом. Для настоящего провайдера понадобятся его ключи идемпотентности, сохранённое намерение операции и сверка статуса. Это отдельный последующий этап.

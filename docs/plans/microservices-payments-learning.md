# Учебный проект: микросервисы и платёжные системы

## Цель

Постепенно построить учебный мини-магазин, чтобы разобраться в архитектуре микросервисов и жизненном цикле платежей: создание заказа → создание платежа → подтверждение оплаты → изменение статуса заказа.

Начинаем с двух NestJS-сервисов и минимального клиентского приложения. Затем добавляем симулятор внешнего платёжного провайдера, брокер сообщений и реальные тестовые интеграции.

## Стек

- Бэкенд: NestJS + TypeScript.
- Клиент: React + TypeScript + Vite.
- UI: shadcn/ui + Tailwind CSS.
- HTTP-запросы клиента: Axios.
- Состояние клиента: локальное состояние React; MobX, только если потребуется общий store.
- Хранение данных: PostgreSQL, отдельная база и учётные данные для каждого бизнес-сервиса. Локально допустим один сервер PostgreSQL.
- Локальная инфраструктура: Docker Compose.
- Документация HTTP API: Swagger.
- Асинхронное взаимодействие на следующих этапах: RabbitMQ.

Не добавляем на старте Kubernetes, отдельный API Gateway, сложную авторизацию и лишние библиотеки управления состоянием.

## Структура репозитория

```text
apps/
├── client/                       # Учебная панель на React
├── orders-service/               # Заказы, NestJS
├── payments-service/             # Платежи, NestJS
└── payment-provider-simulator/    # Симулятор провайдера, добавляется позже
docs/
└── plans/
```

Один репозиторий, отдельные приложения и процессы. Сервисы не обращаются напрямую к базам данных друг друга.

## Сервисы

### orders-service

Отвечает за создание заказов, расчёт суммы и статус заказа.

Начальные HTTP-эндпоинты:

- `POST /orders` — создать заказ на выбранный тестовый товар.
- `GET /orders` — получить список заказов для интерфейса.
- `GET /orders/:id` — получить заказ и его статус.
- `POST /orders/:id/pay` — начать оплату выбранным способом.

Стоимость определяется сервером, а не принимается от клиента как доверенное значение.

### payments-service

Отвечает за создание платежей, взаимодействие с провайдерами, проверку уведомлений и хранение статусов платежей.

Начальный HTTP API:

- `POST /payments` — внутренний запрос от orders-service на создание платежа.
- `GET /payments/:id` — получить платёж и его статус.
- `POST /webhooks/:provider` — принять уведомление провайдера.

Адаптеры провайдеров имеют единый интерфейс. Начинаем с `MockPaymentProvider`, затем добавляем адаптеры выбранных реальных провайдеров и криптоплатежей.

Карта и СБП — способы оплаты, не обязательно разные провайдеры или микросервисы. Один провайдер может поддерживать несколько способов оплаты.

### payment-provider-simulator

Добавляется после базового сценария. Изначально фиктивная оплата находится внутри payments-service, затем симулятор выносится в отдельное приложение.

Симулирует:

- успешную оплату;
- отказ и истечение срока платежа;
- задержку webhook;
- повторную доставку webhook;
- ситуацию, когда запрос завершился таймаутом, но платёж у провайдера был создан.

Управляющие операции симулятора доступны только в учебном режиме и не могут подтверждать настоящие платежи.

## Взаимодействие

### Сначала HTTP

Микросервисы могут взаимодействовать через обычный HTTP; брокер не является обязательным условием микросервисной архитектуры.

1. Клиент создаёт заказ в orders-service.
2. Пользователь выбирает способ оплаты.
3. orders-service передаёт payments-service идентификатор заказа и рассчитанную сервером сумму.
4. payments-service создаёт платёж у фиктивного или внешнего провайдера.
5. Клиент получает ссылку на оплату либо данные для QR-кода, если сценарий это поддерживает.
6. Провайдер отправляет webhook в payments-service.
7. payments-service проверяет уведомление и сохраняет результат.
8. orders-service получает результат через внутреннее HTTP-взаимодействие и обновляет заказ. Конкретный контракт фиксируется при реализации этого этапа.
9. Клиент запрашивает актуальное состояние и показывает новый статус.

Возврат пользователя на страницу успешной оплаты сам по себе не является доказательством платежа. Подтверждение происходит через серверное взаимодействие с провайдером.

### Затем RabbitMQ

- Создание платежа остаётся синхронным запросом.
- Результаты передаются событиями `payment.succeeded` и `payment.failed`.
- orders-service обрабатывает события идемпотентно.
- Изучаем подтверждения доставки, повторные попытки, дубликаты и недоступность потребителя.
- После базового обмена добавляем transactional outbox, чтобы сохранённое изменение не потеряло соответствующее событие при аварии.

Клиент работает только с HTTP API, без прямого доступа к PostgreSQL или RabbitMQ. Секретные ключи провайдеров остаются на бэкенде.

## Минимальный клиент

### Заказы

- Создание заказа на выбранный тестовый товар.
- Список заказов и их статусы.
- Детали заказа и выбор способа оплаты.

### Оплата

- Создание платежа.
- Отображение ссылки на платёжную страницу либо QR-кода при поддержке сценария.
- Просмотр и обновление статуса платежа.

### Учебная панель симулятора

- «Оплатить успешно».
- «Отклонить платёж».
- «Повторить webhook».
- Позже — задержки и другие сбои.

### Журнал запросов

Для запросов Axios показываем HTTP-метод, URL, код ответа и JSON, чтобы было понятно, какие ручки вызывает интерфейс. Чувствительные данные и секреты не выводим.

## Этапы реализации и обучения

### 1. Два сервиса, клиент и фиктивная оплата

- Создать client, orders-service и payments-service.
- Организовать HTTP-взаимодействие сервисов.
- Добавить фиктивного провайдера внутри payments-service.
- Сделать интерфейс заказов, платежей и учебного подтверждения оплаты.
- Добавить Swagger и отображение ошибок в интерфейсе.

Первый законченный сценарий: создать заказ в интерфейсе → начать фиктивную оплату → подтвердить её через учебную панель → увидеть обновлённый статус заказа.

### 2. Хранение данных и отдельный симулятор

- Добавить PostgreSQL с изоляцией данных сервисов.
- Вынести симулятор провайдера в третье приложение.
- Реализовать асинхронные уведомления и переходы статусов.
- Проверить, что состояние сохраняется после перезапуска.

### 3. Повторные запросы и сбои

- Идемпотентность создания платежа.
- Несколько попыток оплаты одного заказа.
- Повторные и задержанные webhook.
- Таймауты и безопасные повторные попытки.
- Сверка статуса с провайдером при потере уведомления.

### 4. RabbitMQ и события

- Заменить HTTP-уведомление о результате платежа событиями.
- Проверить доставку после временной недоступности orders-service.
- Обработать дубликаты событий.
- Добавить transactional outbox отдельным последующим шагом.

### 5. Российские карты и СБП в тестовом режиме

- Выбрать провайдера после проверки актуальной документации и возможностей тестовой среды.
- Реализовать авторизацию API, создание платежа и обработку уведомлений по требованиям провайдера.
- Проверить карточный сценарий и СБП в пределах возможностей выбранной тестовой среды.
- Добавить сверку статусов.

Доступность тестовых сценариев необходимо проверить перед интеграцией. Приём настоящих платежей обычно требует регистрации и подключения у провайдера.

### 6. Криптоплатежи

- Начать с симулятора или testnet, без реальных средств.
- Изучить выбор сети, подтверждения, срок действия платежа и курс.
- Обработать недоплату и переплату.
- Определить точность и единицы хранения сумм для выбранного актива.
- Не хранить приватные ключи в приложении.

## Правила работы с платежами

- Повторный запрос не должен создавать случайный второй платёж.
- У одного заказа может быть несколько попыток оплаты.
- Webhook может приходить несколько раз; обработка должна быть идемпотентной.
- Переходы статусов должны быть явными и защищать от некорректных повторных обновлений.
- Рублёвые суммы хранятся целым числом копеек, без float.
- Сумму заказа определяет сервер.
- Статус можно сверить с провайдером, если webhook потерялся.
- Подлинность уведомлений проверяется способом, предусмотренным конкретным провайдером.
- PAN/CVV не проходят через наши сервисы и не сохраняются; используется платёжная страница провайдера.
- Учебное управление результатами оплаты изолировано от реальных интеграций.

## Подход к обучению

Не генерировать сразу весь проект со сложной инфраструктурой. На каждом этапе разбирать изменения, запускать законченный сценарий и проверять ошибки и сбои. Первые интеграции — только фиктивные и тестовые; реальные платежи не входят в начальный объём работ.

# Payments Lab

Учебный мини-магазин: **два микросервиса NestJS и клиент React**. Сервисы общаются по HTTP, каждый хранит данные в своей PostgreSQL. Платежи, ключи идемпотентности и состояние уведомлений переживают перезапуск приложений. Платёжный провайдер пока фиктивный.

**Настоящих платежей нет.** Карта, СБП и криптовалюта пока только варианты одного mock-сценария. Банки, блокчейн, QR-коды и платёжные страницы не подключены.

## Быстрый старт

Нужны Node.js 22.14+, npm и запущенный Docker с Docker Compose v2. PostgreSQL запускается в контейнере; RabbitMQ пока не нужен.

```bash
npm install
npm run db:up
npm run db:migrate
npm run dev
```

| Приложение       | Адрес                      |
| ---------------- | -------------------------- |
| Клиент           | http://localhost:5173      |
| orders-service   | http://127.0.0.1:3001      |
| payments-service | http://127.0.0.1:3002      |
| Swagger заказов  | http://127.0.0.1:3001/docs |
| Swagger платежей | http://127.0.0.1:3002/docs |

Копировать `.env` для первого запуска не требуется: локальные значения заданы по умолчанию. Остановка приложений — `Ctrl+C`; PostgreSQL продолжает работать отдельно. `npm run db:down` останавливает базу без удаления данных.

| База    | Адрес             | База / пользователь | Пароль           |
| ------- | ----------------- | ------------------- | ---------------- |
| Заказы  | `127.0.0.1:15432` | `orders`            | `orders_local`   |
| Платежи | `127.0.0.1:15434` | `payments`          | `payments_local` |

Это исключительно локальные учебные реквизиты. PostgreSQL запущены в отдельных контейнерах и используют отдельные именованные volumes. Роли приложений не имеют прав суперпользователя и не подключаются к чужой базе.

При переходе с первого этапа достаточно снова выполнить `npm install`, `npm run db:up` и `npm run db:migrate`. Ранее утраченные in-memory платежи восстановить нельзя. Существующие заказы не удаляются; старые оплаченные заказы защищены от создания нового платежа. Для экспериментов с новым хранилищем создавай новые заказы.

### Первый эксперимент

1. Открой клиент и создай заказ.
2. Выбери способ оплаты и нажми «Создать платёж».
3. Нажми «Успешно» в учебном симуляторе.
4. Убедись, что платёж успешен, уведомление доставлено, а заказ оплачен.
5. Нажми «Повторить уведомление»: второй заказ или платёж не появится.
6. Создай другой заказ, отклони платёж и создай новую попытку оплаты.
7. Раскрой записи журнала запросов и сравни тела запросов и ответов. Межсервисные вызовы смотри в терминале.

## Что здесь является микросервисами

```text
React-клиент
    │ HTTP через dev-proxy Vite
    ├─────────────────────────────┐
    ▼                             ▼
orders-service                payments-service
  заказы                        платежи
  своя PostgreSQL               своя PostgreSQL
    │                             ▲
    └── POST /payments ────────────┘
    ▲                             │
    └── POST /internal/           │
        payment-results ──────────┘
```

- Это **два независимых процесса**, а не два модуля одного сервера.
- У каждого своя ответственность и собственные данные.
- orders-service не читает таблицы платежей и не импортирует PaymentsService; он вызывает HTTP API.
- Общий репозиторий и npm workspaces упрощают запуск, но не объединяют приложения в один процесс.
- NestJS `@nestjs/microservices` и брокер не обязательны для такой архитектуры. RabbitMQ добавим позже и сравним подходы.

### Границы ответственности

**orders-service** знает каталог, количество, сумму и состояние заказа. Он определяет цену на сервере. Клиент отправляет `productId` и `quantity`, но не цену.

**payments-service** знает попытку оплаты, сумму, метод, результат и доставку уведомления. Он не должен управлять содержимым заказа.

У одного заказа может быть несколько неуспешных попыток оплаты. Одновременно разрешён только один незавершённый платёж; после успеха новый платёж создать нельзя.

## Как читать бэкенд

У обоих сервисов одинаковый базовый каркас:

| Файл                    | Роль                                                              |
| ----------------------- | ----------------------------------------------------------------- |
| `src/main.ts`           | Запуск Nest-приложения, порт, CORS, глобальная валидация, Swagger |
| `src/app.module.ts`     | Регистрация контроллеров и провайдеров в контейнере Nest          |
| `src/*.controller.ts`   | HTTP-маршруты, чтение тела, параметров и заголовков               |
| `src/*.service.ts`      | Правила предметной области и межсервисные запросы                 |
| `src/dto.ts`            | Классы входных данных с runtime-валидацией                        |
| `src/internal.guard.ts` | Проверка токена внутренних запросов                               |

В payments-service есть `src/mock-payment.provider.ts` — начальная точка для будущих адаптеров провайдеров. Пока он только создаёт фиктивное состояние `pending`, без внешнего API.

Хранение выделено в `orders.repository.ts` и `payments.repository.ts`. Entity-классы каждого сервиса находятся в его `src/database/entities`, явные SQL-миграции — в `src/database/migrations`. DTO, модель хранения и HTTP-ответ — разные роли, даже если некоторые поля совпадают.

### Контроллер, сервис и dependency injection

`@Controller()` делает класс входной точкой HTTP. Например, `@Post('orders')` связывает метод с `POST /orders`.

Контроллер получает `OrdersService` через конструктор, а не создаёт его через `new`. Nest видит сервис в `providers` модуля и самостоятельно передаёт экземпляр. Это dependency injection: HTTP-слой отделён от бизнес-логики.

`@Injectable()` помечает класс как участника этого механизма. Сам по себе декоратор не регистрирует сервис — нужна также регистрация в модуле.

### Зачем DTO, если уже есть TypeScript

TypeScript не проверяет JSON, пришедший по сети: его типы исчезают при компиляции. `ValidationPipe` и декораторы `class-validator` проверяют входные значения во время выполнения.

Например, количество должно быть целым числом от 1 до 10. Дополнительное поле `amount` в создании заказа отклоняется с `400`, а не молча принимается. `ParseUUIDPipe` проверяет формат идентификаторов в URL.

### Полный путь оплаты

1. `POST /orders` создаёт заказ со статусом `pending`, сумма — целое число копеек.
2. `POST /orders/:id/pay` требует `Idempotency-Key` и метод оплаты.
3. OrdersService вызывает `POST /payments` через Axios, передавая рассчитанную сумму и внутренний токен.
4. PaymentsService сохраняет попытку оплаты со статусом `pending`. OrdersService сохраняет её ID в заказе.
5. Учебная кнопка вызывает `POST /payments/:id/mock-result`. **Это не настоящий webhook провайдера**, а явная имитация его результата.
6. PaymentsService сохраняет `succeeded` или `failed`, затем отправляет внутреннее уведомление orders-service.
7. OrdersService сверяет платёж через `GET /payments/:id`: заказ, сумму, валюту и статус. Только после этого успешный платёж переводит заказ в `paid`.
8. Клиент перечитывает данные и показывает результат.

Повтор создания с тем же ключом получает прежний платёж из БД, а не запускает новую оплату. Он также восстанавливает связь с заказом и статус `paid`, если предыдущий ответ или уведомление потерялись. Для уже оплаченного заказа orders-service использует внутренний `POST /payments/lookup`: только поиск существующего платежа, без возможности вставки новой записи.

Взаимодействие двунаправленное, но не образует бесконечного цикла: чтение платежа в шаге 7 не отправляет новых уведомлений.

### Идемпотентность

Если запрос завис, это **не означает**, что операция не выполнилась. Поэтому одна попытка оплаты имеет один `Idempotency-Key`.

- Повтор с тем же ключом и методом возвращает тот же платёж, в актуальном состоянии.
- Тот же ключ с другими данными даёт `409 Conflict`.
- Уникальность `(order_id, idempotency_key)` защищает от дублей между процессами и после перезапусков. Отдельный частичный уникальный индекс запрещает второй `pending` или `succeeded` для заказа.
- После сетевой ошибки клиент сохраняет ключ для повтора. После отказа создаётся новая попытка с новым ключом.
- Повторное уведомление не меняет смысл уже обработанного результата.
- Финальный статус платежа нельзя переключить с успешного на отказ или наоборот.

Ключ хранится в той же строке, что и платёж: не бывает сохранённого платежа без сохранённого ключа. `Map` и локальных блокировок в сервисах больше нет. Старый ключ после отказа по-прежнему возвращает старую неуспешную попытку; для новой нужен новый ключ. Одинаковый ключ у разных заказов допустим. Это идемпотентность записи фиктивного платежа, не гарантия «ровно одного» внешнего списания у ещё не подключённого провайдера.

### Платёж и уведомление — разные состояния

```text
payment.status:              pending → succeeded | failed
payment.notificationStatus:  not_sent → delivered | failed
order.status:                pending → paid
```

Если платежи сохранили `succeeded`, но заказы недоступны, платёж остаётся успешным, а `notificationStatus` становится `failed`. HTTP-ответ учебной кнопки в этом случае всё ещё успешен: результат симуляции сохранён, но доставка отдельно помечена ошибкой.

Статус и счётчик начатых попыток уведомления записываются транзакционно до HTTP-вызова. `delivered` означает, что хотя бы одна доставка подтверждена: последующая ошибка повтора не отменяет этот факт. Параллельные подтверждения используют блокировку строки, поэтому финальный результат нельзя поменять с успеха на отказ или обратно.

Кнопка «Повторить уведомление» снова пытается доставить результат. После отказа платежа заказ остаётся `pending`, чтобы можно было оплатить его ещё раз. Старый отказ не может отменить уже оплаченный заказ.

Автоматической гарантированной доставки пока нет: её изучим через RabbitMQ, повторы и outbox.

## API

### orders-service, порт 3001

| Метод | Путь                        | Назначение                                                          |
| ----- | --------------------------- | ------------------------------------------------------------------- |
| GET   | `/health`                   | Проверка запуска процесса                                           |
| GET   | `/products`                 | Серверный каталог товаров, цены в копейках                          |
| POST  | `/orders`                   | Создать заказ: `{ "productId": "backend-course", "quantity": 1 }`   |
| GET   | `/orders`                   | Список заказов                                                      |
| GET   | `/orders/:id`               | Детали заказа                                                       |
| POST  | `/orders/:id/pay`           | `{ "method": "card" }`, заголовок `Idempotency-Key`                 |
| POST  | `/internal/payment-results` | Внутренний результат: `orderId`, `paymentId`, `status`; нужен токен |

### payments-service, порт 3002

| Метод | Путь                        | Назначение                                                            |
| ----- | --------------------------- | --------------------------------------------------------------------- |
| GET   | `/health`                   | Проверка запуска процесса                                             |
| POST  | `/payments`                 | Внутреннее создание платежа; нужен токен                              |
| POST  | `/payments/lookup`          | Внутренний поиск по данным создания и ключу, без вставки; нужен токен |
| GET   | `/payments/:id`             | Статус платежа и доставки уведомления                                 |
| POST  | `/payments/:id/mock-result` | Учебное подтверждение: `{ "status": "succeeded" }` или `failed`       |

Поддерживаемые значения метода: `card`, `sbp`, `crypto`. Во всех трёх случаях сумма пока в RUB: настоящей конвертации в криптоактив нет.

Стандартные ответы: `400` — невалидный запрос; `401` — нет внутреннего токена; `404` — объект не найден; `409` — конфликт состояния или ключа; `502` — ошибка вызова payments-service. POST-операции возвращают `201`, кроме внутреннего поиска `/payments/lookup`, который возвращает `200`. Повтор публичного `/orders/:id/pay` сохраняет статус `201`, даже когда возвращает уже существующий платёж.

## Конфигурация

Примеры — `apps/orders-service/.env.example` и `apps/payments-service/.env.example`. При необходимости скопируй каждый в `.env` **в той же папке приложения**.

- `PORT` — порт соответствующего сервиса.
- `CLIENT_ORIGIN` — разрешённый origin браузера при прямом обращении к сервису.
- `PAYMENTS_SERVICE_URL` / `ORDERS_SERVICE_URL` — адрес соседнего сервиса.
- `INTERNAL_API_TOKEN` — одинаковое значение в обоих сервисах, передаётся в `x-internal-token`.
- `DATABASE_URL` — URL собственной PostgreSQL в `.env` соответствующего сервиса; у сервисов разные значения.

В браузер этот токен не передаётся. Для ручного вызова внутренних эндпоинтов через Swagger используй Authorize и локальное значение `local-learning-only` либо своё из `.env`.

Vite проксирует `/api/orders/*` и `/api/payments/*` на локальные сервисы. Это только удобство разработки, **не отдельный production API Gateway**. Если поменяешь порты бэкендов, обнови proxy в `apps/client/vite.config.ts`. Статический preview не заменяет dev-proxy.

## Команды и проверки

```bash
npm run dev          # три приложения с перезапуском при изменении исходников
npm run typecheck    # TypeScript во всех приложениях
npm run build        # клиент и два сервиса
npm test             # сборка + интеграционные тесты
npm run format       # отформатировать исходники и конфигурацию
npm run format:check # проверить форматирование без изменения файлов
npm run db:up        # запустить обе dev-базы и дождаться готовности
npm run db:down      # остановить обе dev-базы, сохранив volumes
npm run db:migrate   # применить миграции обоих сервисов
npm run db:migrations # посмотреть миграции обоих сервисов
npm run db:test:down # остановить обе отдельные тестовые PostgreSQL
```

Единый стиль задаёт Prettier в `.prettierrc.json`: отступ 2 пробела, одинарные кавычки в JS/TS, точки с запятой и целевая длина строки 100 символов. `.editorconfig` задаёт базовые настройки редактора. Зависимости, результаты сборки и lock-файлы исключены из форматирования.

Сервисы компилируются обычным TypeScript; `tsc-watch` перезапускает процесс после успешной компиляции. Nest CLI для запуска не требуется.

Можно запускать по одному в отдельных терминалах:

```bash
npm run dev -w @lab/orders-service
npm run dev -w @lab/payments-service
npm run dev -w @lab/client
```

`npm test` собирает приложения, запускает отдельные тестовые PostgreSQL на портах 15433 и 15435 и выполняет `tests/integration.test.mjs`. На каждый прогон создаются две базы со случайными именами; после завершения они удаляются. Dev-базы не очищаются и не используются тестами. Тестовые контейнеры остаются запущенными до `npm run db:test:down`.

Тесты запускают настоящие сервисы на портах 3101/3102, а для проверки гонок — вторые реплики на 3103/3104. Проверяются HTTP-сценарии, миграции и их откат, ограничения БД, транзакции, восстановление после потери ответа, перезапуск обоих сервисов, конкурентное создание и финализация. Тест сбоя использует SIGSTOP/SIGCONT (macOS/Linux). Для `npm run test:integration` без сборки сначала нужны собранные приложения и `npm run db:test:up`. Адреса тестовых серверов можно задать через `TEST_DATABASE_URL` (заказы) и `TEST_PAYMENTS_DATABASE_URL` (платежи); роли должны уметь создавать отдельные тестовые базы.

## Клиент в общих чертах

`apps/client` — React + TypeScript + Vite, shadcn/ui и Tailwind. Axios-клиенты и журнал запросов находятся в `src/lib/api.ts`. Состояние локальное, MobX пока не нужен. В интерфейсе — создание и выбор заказа, оплата, симулятор результата, просмотр запросов и ошибок.

## Текущие ограничения

- Сохранение данных защищает от перезапуска, но не от удаления volume или административного изменения таблиц. Старые платежи, утраченные до этого этапа, не восстанавливаются автоматически.
- Клиент хранит ключ текущей попытки только до перезагрузки страницы. Для повтора потерянного запроса нужно знать исходный ключ; сервер не может угадать его за клиента. Автоматическую сверку незавершённых операций пока не добавляем.
- Каталог товаров пока задан в коде; в позицию заказа записывается снимок названия и цены. API создаёт ровно одну позицию; таблица допускает несколько, но поддержки корзины в API ещё нет.
- Пока нет брокера, автоматической сверки статусов, outbox и настоящих провайдеров. Доставка уведомления по-прежнему запускается вручную через симулятор, а не гарантируется фоновым worker.
- Есть окна рассогласования: платёж и заказ сохраняются в разных транзакциях разных баз. Повтор исходного запроса с тем же ключом восстанавливает локальную связь и успешный статус, но сам по себе не запускается автоматически.
- Нет пользовательской авторизации. Чтение и mock-управление доступны любому локальному клиенту. Межсервисный токен — только простая учебная защита, не полноценная production-аутентификация.
- CORS не является авторизацией. Приложения слушают только loopback; не публикуй этот стенд в интернете.
- При `NODE_ENV=production` бэкенды отказываются запускаться. Это не делает стенд безопасным для внешнего доступа в другом режиме.
- PAN/CVV, реальные средства, кошельки и приватные ключи здесь не используются.

# Этап 4.2: transactional outbox/inbox

## 1. Проблема: почему одной очереди недостаточно

RabbitMQ хранит принятое сообщение, но не знает о транзакциях нашей PostgreSQL. Раньше существовало окно:

```text
Платёж succeeded закоммичен → процесс упал → событие не опубликовано
```

Переподключение к брокеру не восстанавливало событие: HTTP-запроса, который собирался его отправить, уже нет. Требовался ручной повтор.

Теперь вместе с результатом сохраняется долговечное **задание отправки**. После восстановления worker продолжает работу автоматически. Outbox закрывает промежуток до передачи ответственности брокеру; inbox предотвращает повторное применение после доставки consumer.

## 2. Где читать реализацию

| Файл                                                                   | Ответственность                            |
| ---------------------------------------------------------------------- | ------------------------------------------ |
| `apps/payments-service/src/payments.repository.ts`                     | Результат и outbox одной транзакцией       |
| `apps/payments-service/src/database/entities/payment-outbox.entity.ts` | Структура задания                          |
| `apps/payments-service/src/outbox/outbox.repository.ts`                | Захват, lease, повтор и отметка публикации |
| `apps/payments-service/src/outbox/outbox.worker.ts`                    | Фоновый цикл независимо от HTTP-запроса    |
| `apps/payments-service/src/payment-events.publisher.ts`                | AMQP-отправка с publisher confirm          |
| `apps/orders-service/src/orders.repository.ts`                         | Inbox и заказ одной транзакцией            |
| `apps/orders-service/src/payment-events.consumer.ts`                   | Получение, ack, retry и DLQ                |

Worker — фоновый компонент внутри payments-service, не новый бизнес-сервис. Каждая реплика может иметь свой worker. В будущем его можно выделить в отдельный процесс, сохранив протокол захвата.

## 3. Атомарно сохранить факт и задание

При подтверждённом результате провайдера:

```text
BEGIN
  SELECT payment FOR UPDATE
  проверить переход статуса
  UPDATE payments SET status, result_event_id, result_recorded_at
  INSERT payment_outbox с неизменяемым payload, если задания ещё нет
COMMIT
```

Обе записи либо сохранятся, либо откатятся. Если outbox записать не удалось, финальный статус у нас тоже не фиксируется. Провайдер при этом мог уже провести оплату: его состояние отдельно, поэтому webhook нужно повторить или сверить результат позднее.

HTTP и AMQP в этой транзакции не выполняются. Завершение webhook теперь означает «факт и задание сохранены», а не «брокер уже получил сообщение». RabbitMQ может быть выключен — подтверждать приём провайдеру это не мешает.

## 4. Почему хранится payload, а не только ID платежа

Worker отправляет сохранённый JSON-снимок факта, а не пересобирает его из потенциально изменившихся таблиц. Повтор использует тот же eventId и содержание.

Первичный ключ event_id и уникальность payment_id соответствуют текущей модели: у одной попытки оплаты один неизменяемый финальный результат. Для возвратов и дополнительных типов событий схему придётся расширить.

Повтор webhook или sync не создаёт новое задание и не сбрасывает опубликованное в pending. Внешний eventId провайдера и внутренний eventId доставки остаются разными идентификаторами.

## 5. Состояния outbox

```text
pending → processing → published
             │
             └── ошибка → pending с next_attempt_at

processing с истёкшим lease → processing с новым токеном
```

- attempts — число захватов для попытки отправки, не число сообщений, гарантированно дошедших до брокера.
- next_attempt_at — когда разрешён повтор.
- locked_until — срок временного владения.
- locked_by — уникальный токен конкретного захвата, не постоянное имя процесса.
- last_error — последняя причина неудачи.
- published_at — фиксация подтверждения брокера, не обработки заказа.

published-записи не удаляются автоматически: это история. Для production нужны retention, архивирование и мониторинг размера таблиц.

## 6. Захват: зачем FOR UPDATE SKIP LOCKED

Два worker не должны одновременно считать одну строку свободной. Каждый открывает короткую транзакцию, выбирает одно готовое задание, записывает token и lease, увеличивает attempts и коммитит.

FOR UPDATE запрещает конкурентный захват строки до коммита. SKIP LOCKED позволяет второй реплике забрать другую строку, не ожидая первую. LIMIT 1 не даёт случайно заблокировать целую пачку, собираясь обработать одну запись.

В той же транзакции увеличивается совместимый notificationAttempts платежа. После коммита row lock освобождён: во время AMQP-ожидания SQL-транзакция не удерживается.

## 7. Почему нужны и lease, и токен

Блокировка защищает лишь короткий SQL-захват. Если затем worker погибнет, явно освободить задание некому. Поэтому после locked_until другой worker может его подхватить. Время вычисляет PostgreSQL, а не разные локальные часы Node.js.

Первый worker мог не погибнуть, а просто зависнуть. Его поздний ответ не должен перезаписать новое владение. Успех и ошибка записываются только при условии:

```text
WHERE event_id = наш_event_id
  AND locked_by = наш_token
  AND status = processing
```

Если токен сменился, UPDATE не затрагивает строку. Это fencing сохранения результата. Но токен не отменяет AMQP-вызов старого worker: копия всё ещё могла уйти. Поэтому inbox всё равно необходим.

Lease по умолчанию 30 секунд, публикация ограничена таймаутом транспорта. Если она затянулась дольше lease, возможны дубли, но старый token не уничтожит новое владение. В тестах lease сокращён до двух секунд.

## 8. Confirm, отметка и повтор

После publisher confirm worker одной транзакцией отмечает outbox published и меняет notificationStatus платежа. Если confirm потерян или отметка не сохранилась, возможен повтор той же отправки.

При ошибке job возвращается в pending. Задержка растёт экспоненциально от 500 мс до 30 с, сохраняется в next_attempt_at и не сбрасывается при рестарте.

Outbox повторяется без фиксированного лимита: временная недоступность брокера не должна навсегда выбросить сохранённый факт. Это отличается от consumer retry: неисправимое входящее сообщение идёт в DLQ. Повреждённые вручную задания и неверную конфигурацию оператор должен разбирать по last_error — worker их не исправит.

Внутри одной реплики цикл не перекрывается сам с собой. За проход обрабатывается до десяти заданий, каждое захватывается отдельно. Это понятный учебный polling-worker, не высокопроизводительный CDC-relay.

## 9. Окно после отправки

```text
Брокер подтвердил событие → worker погиб → published не записан
```

После lease новый worker отправит тот же eventId. Это ожидаемо: общей транзакции PostgreSQL + RabbitMQ нет. Отмечать published заранее нельзя — авария до отправки потеряет сообщение.

Следовательно, доставка остаётся at-least-once, даже при наличии outbox.

## 10. Inbox: однократное применение в своей БД

OrdersRepository начинает транзакцию и вставляет eventId в payment_inbox через ON CONFLICT DO NOTHING:

- вставка успешна → проверяет и блокирует заказ, меняет его и коммитит обе записи;
- eventId уже есть с тем же содержимым → пропускает бизнес-обновление;
- eventId есть с другим содержимым → PermanentMessageError и DLQ.

Если после вставки inbox изменение заказа не удалось, откатывается и receipt. Повтор не будет ошибочно считаться уже обработанным.

Конкурентные INSERT одного eventId сериализуются уникальным ключом PostgreSQL. Если первый коммитится, второй видит готовую receipt; если откатывается, второй может вставить её и применить событие. JavaScript-проверки «есть ли ключ» недостаточно.

order_id здесь — диагностическая ссылка. Receipt коммитится только вместе с проверкой существования заказа и его обновлением; неизвестный заказ или неверная сумма откатывают её.

## 11. Что считается тем же содержимым

В inbox сохраняется SHA-256 канонического списка полей. Это не хэш сырой JSON-строки: пробелы, порядок ключей и регистр UUID не меняют смысл события.

В хэш входят тип, версия, paymentId, orderId, сумма, валюта и нормализованное время. Повторное использование eventId с другой суммой или другим платежом — ошибка источника, а не безопасный дубликат. Хэш не заменяет аутентификацию: право публикации защищается доступом к брокеру.

## 12. Ack после COMMIT

Если процесс упадёт после изменения заказа, но до ack, брокер доставит сообщение заново. Inbox позволит подтвердить его без повторного UPDATE заказа.

Гарантия действует **в пределах этой PostgreSQL-транзакции и сохранённой inbox-истории**. Письмо, выдача товара в другом сервисе или HTTP-вызов не становятся автоматически атомарными вместе с ней. Для новых внешних эффектов потребуется своё долговечное задание и/или идемпотентность.

Нельзя бездумно чистить inbox: после удаления ключа поздний replay снова сможет применить событие. Retention должен учитывать сроки повторов и восстановления очередей/outbox.

## 13. Переход с прошлого этапа

Миграции добавляют таблицы без удаления платежей и заказов. Старые финальные платежи переносятся в outbox:

- published и исторический delivered считаются уже переданными;
- неподтверждённые результаты становятся pending;
- прежние eventId и время сохраняются; если их нет — создаются ID и время фиксации при миграции, а не выдумывается историческое время оплаты.

Для опубликованной истории published_at при backfill означает время переноса, не точный старый момент confirm. Inbox не угадывает обработки до своего появления: первый replay старого события может один раз выполнить уже идемпотентное обновление и создать receipt.

Откат outbox-миграции удаляет задания и отменяет новую гарантию. Не выполняй его на рабочей базе без плана; down проверяется автоматически только в одноразовых тестовых базах.

## 14. Посмотреть данные

```bash
docker compose exec payments-db psql -U payments -d payments
```

```sql
SELECT event_id, payment_id, status, attempts, next_attempt_at,
       locked_by, locked_until, published_at, last_error
FROM payment_outbox ORDER BY created_at DESC;

SELECT payload FROM payment_outbox ORDER BY created_at DESC LIMIT 1;
```

В другой базе:

```bash
docker compose exec orders-db psql -U orders -d orders
```

```sql
SELECT event_id, event_type, order_id, payload_hash, processed_at
FROM payment_inbox ORDER BY processed_at DESC;
```

Не сбрасывай published в pending без причины. Для осознанного replay сохраняй исходный eventId и payload: обработанный факт отсеется inbox. Исправление и повтор DLQ — отдельная операторская задача.

## 15. Эксперименты и границы

Выключи только RabbitMQ, оплати новый заказ у симулятора, посмотри pending-задание и last_error. Запусти брокер: worker сам доставит событие, ручной sync не требуется.

Для окна перед отправкой запусти единственную реплику платежей с OUTBOX_WORKER_ENABLED=false. Результат создаст outbox без публикации. Перезапусти с true — задание уйдёт автоматически. При выключении всех worker доставка ожидаемо стоит.

Потерянный **внешний** webhook по-прежнему требует сверки: пока payments-service не узнал факт, outbox нечего сохранять. Также не покрыты удаление volume, ручная порча данных и неразобранная DLQ.

Тесты воспроизводят SIGKILL после коммита, потерю отметки после отправки, потерю ack, rollback обеих локальных транзакций, два worker, SKIP LOCKED, истечение lease, старый token и коллизию eventId. Dev-базы и dev-брокер при этом не используются.

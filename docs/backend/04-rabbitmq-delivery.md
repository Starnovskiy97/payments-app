# Этап 4.1: RabbitMQ — от «вызвать сейчас» к «обработать, когда сможешь»

## 1. Проблема и граница этого шага

Раньше после подтверждения оплаты payments-service делал HTTP-вызов заказов. Если заказы выключены, результата оплаты в их базе нет до ручного повтора.

Теперь между сервисами есть посредник — RabbitMQ. Платежи передают ему сообщение, а заказы забирают сообщение, когда доступны. **Это не делает весь процесс безусловно надёжным:** промежуток между коммитом платежа и его публикацией пока остаётся. Outbox/inbox — следующий самостоятельный шаг.

```text
Провайдер ── HTTP webhook ──> payments-service
                                    │
                             payment.succeeded
                                    ▼
                                RabbitMQ
                                    │
                                    ▼
                              orders-service
```

Создание заказа и платежа остаётся HTTP request/response: пользователю нужен результат создания и checkoutUrl. Webhooks внешнего провайдера тоже остаются HTTP: внешний провайдер не подключается к нашему брокеру.

## 2. Запуск: что именно добавилось

```bash
npm install
npm run db:up
npm run mq:up
npm run db:migrate
npm run dev
```

RabbitMQ слушает AMQP на 5672, Management UI — http://127.0.0.1:15672. Локальная учётная запись: lab / lab_local. `npm run mq:down` останавливает его без удаления volume.

Hostname контейнера фиксирован, данные сохраняются в именованном volume. Очереди — durable quorum queues; сообщения публикуются persistent и с publisher confirms. В нашем стенде всего **один узел**, поэтому quorum не означает отказоустойчивый кластер. Перезапуск контейнера покрывается; утрата диска или volume — нет.

Оба бизнес-сервиса используют одинаковые RABBITMQ_URL и RABBITMQ_QUEUE_PREFIX. HTTP-серверы могут запуститься при недоступном брокере, а AMQP-транспорт подключается повторно. `/health` содержит rabbitmq: connected/disconnected. Это признак подключения, не доказательство успешной бизнес-обработки.

## 3. Producer, exchange, queue и consumer

- **Producer** — payments-service: публикует факт результата оплаты.
- **Exchange** — встроенный default exchange с именем пустая строка. В этом первом примере routing key равен имени очереди.
- **Queue** — место, где сообщение ожидает обработки.
- **Consumer** — orders-service: читает и применяет факт к своей базе.

Очередь результатов: payments-lab.orders.payment-results. Если запустить две реплики заказов, они **конкурируют** за сообщения одной очереди, а не получают по копии каждая. Это балансировка обработки, не broadcast. Если позже появится ещё один независимый подписчик, например уведомления, ему понадобится своя очередь и соответствующая маршрутизация.

Для начала default exchange выбран намеренно: можно изучить доставку, не добавляя сразу topic/fanout-топологию.

## 4. Почему событие — не команда

Сообщение payment.succeeded говорит «платёж уже успешен», а не «попробуй списать деньги». Orders-service самостоятельно решает, что этот факт означает для заказа.

Контракт находится в `packages/messaging/src/payment-result.event.ts`:

```json
{
  "eventId": "42bb07c0-c98c-4007-bf27-7130816492dc",
  "type": "payment.succeeded",
  "version": 1,
  "paymentId": "1d4573c4-01c9-453c-8f1b-cb20bd34ccfe",
  "orderId": "a72f3e37-d3d1-4acb-b3de-c4222282e3d7",
  "amount": 50000,
  "currency": "RUB",
  "occurredAt": "2026-11-11T12:00:00.000Z"
}
```

paymentId обозначает платёж, eventId — факт его финализации. Это не eventId внешнего webhook: внешний протокол и внутренний контракт независимы. Версия позволяет явно отказать в обработке незнакомого формата, а не молча интерпретировать его неправильно.

Новая миграция сохраняет result_event_id и result_recorded_at вместе с финальным статусом. При повторном webhook или сверке они не меняются. Это стабильная идентичность события, **не outbox**: фонового задания на отправку пока нет.

В общий workspace вынесены только контракт и транспорт. Таблицы, репозитории и бизнес-правила сервисы по-прежнему не разделяют. Приложения подключают пакет по имени @lab/messaging; root build сначала собирает packages, затем apps.

## 5. Publisher confirm: брокер принял, но заказ ещё не обновлён

`PaymentEventsPublisher` строит событие из сохранённого платежа и отправляет его через confirm channel. В sendToQueue есть callback подтверждения. Возвращаемое boolean — только backpressure Node-потока, а не результат доставки.

Дополнительно используется mandatory. Брокер может подтвердить обработку публикации даже когда сообщение не попало ни в одну очередь. В этом случае он отправляет basic.return: транспорт считает такую публикацию ошибкой. Случайный correlationId связывает return с конкретной отправкой, а стабильный messageId — с eventId.

Публикация имеет ограниченный таймаут. Если confirm не получен, нельзя заключить, что сообщения точно нет у брокера. Он мог принять его, а ответ потерялся. Поэтому повтор возможен и обработчик обязан быть безопасен к дубликатам.

Новое значение API notificationStatus — **published**, не delivered. Оно означает «брокер подтвердил приём», а не «заказы применили событие». Старое delivered осталось в схеме только для истории предыдущего HTTP-этапа. notificationAttempts теперь считает начатые попытки публикации, не число уникальных событий.

## 6. Consumer ack: почему строго после COMMIT

`PaymentEventsConsumer` работает с noAck: false и prefetch: 5. Это максимум пяти неподтверждённых доставок на consumer; мы не забираем неограниченное число сообщений сразу.

Порядок обработки:

```text
Получить → проверить JSON и версию → начать транзакцию
        → проверить заказ и сумму → сохранить состояние → COMMIT → ack
```

Если ack сделать до COMMIT, сообщение может исчезнуть раньше записи в базе. Если процесс упал после COMMIT, но до ack, RabbitMQ отправит сообщение повторно. Это нормальный сценарий, не исключительная ошибка брокера.

OrdersRepository блокирует строку заказа на время транзакции. Повтор не добавляет второй paymentId. Успех переводит заказ в paid, а старый отказ не возвращает оплаченный заказ в pending. Это **идемпотентность эффекта состояния**, а не пропуск повторного выполнения: отдельного inbox ещё нет. Для отправки писем, выдачи товара и других побочных эффектов такой защиты будет недостаточно.

Событие может прийти до HTTP-ответа /pay. Поэтому consumer сам сохраняет связь paymentId с заказом, а не отвергает событие только из-за отсутствия ID в массиве. Сумма и валюта должны совпасть с локальным заказом.

Consumer больше не вызывает payments-service, чтобы перечитать платёж. Он доверяет источнику событий через брокер и проверяет контракт и локальные инварианты. Благодаря этому обработка очереди работает даже при выключенном payments-service. Цена такого решения — необходимость защищать право публикации: в production нужны отдельные роли, разрешения, TLS и управление секретами. Общая локальная учётная запись стенда этого не заменяет.

## 7. Временная ошибка и отложенный retry

При временной ошибке, например недоступной таблице/БД, немедленный nack с requeue создал бы горячий цикл: получить → упасть → снова получить тысячи раз.

Здесь consumer публикует копию в очередь .retry, дожидается её confirm и только затем делает ack исходного сообщения. TTL очереди — 2 секунды; после истечения сообщение через DLX возвращается в основную очередь. Заголовок x-lab-retry-count сохраняет число повторов. Допускается пять отложенных повторов, затем — DLQ.

Для переноса через DLX у quorum-очередей включены at-least-once dead-lettering и overflow reject-publish. Это важно: стандартный at-most-once DLX сам по себе оставляет окно потери при переносе. В учебном коде параметры заданы аргументами очереди; в production такие настройки удобнее управлять policies.

Если confirm копии не получен, consumer не подтверждает исходное сообщение и закрывает канал. Брокер вернёт unacked в обработку после переподключения. Если копия уже была принята, возможны обе копии — поэтому идемпотентность нужна и здесь.

prefetch и реплики допускают изменение порядка обработки. Правила переходов не должны зависеть от предположения «старое failed всегда придёт раньше нового succeeded».

## 8. Неисправимое сообщение и DLQ

Невалидный JSON, версия, неизвестный заказ или неверная сумма сами по себе от повтора не исправятся. Такие сообщения сразу отправляются в .dead. Исчерпавшие пять повторов временные ошибки тоже идут туда.

В DLQ сохраняются исходное тело, messageId, счётчик и короткая причина ошибки. Исходное сообщение подтверждается только после confirm публикации в DLQ. Само по себе помещение в DLQ не решает бизнес-проблему: его надо исследовать, исправить источник или данные и осознанно переотправить. Автоматического replay DLQ пока нет.

В Management UI открой Queues and Streams, найди три очереди по префиксу. Ready — ожидают доставки, Unacked — доставлены consumer, но ещё не подтверждены. При просмотре Get messages следи за режимом ack: диагностикой тоже можно удалить сообщение.

## 9. Где остаётся потеря и зачем следующий outbox

```text
PostgreSQL: succeeded сохранён
            ↓
       процесс упал
            ↓
RabbitMQ: публикации ещё не было
```

У брокера нет способа узнать про такое событие. result_event_id в строке платежа сам ничего не отправляет. При недоступном RabbitMQ платёж остаётся успешным, publication помечается failed, а после восстановления нужна сверка или повтор webhook. Транспорт переподключается, но не имеет долговечного буфера публикаций.

Это намеренная граница этапа. Далее outbox сохранит задание отправки в той же транзакции, что результат платежа; worker будет публиковать его независимо от HTTP-запроса. Inbox на стороне заказов сохранит факт обработки eventId в той же транзакции, что заказ. Даже после этого не следует обещать магическое exactly-once для любых внешних эффектов.

## 10. Эксперименты и тесты

Для ручного эксперимента запусти приложения в отдельных терминалах, останови только заказы, оплати у провайдера. У платежа будет published, а в RabbitMQ — Ready/Unacked. Запусти заказы: они обновятся без повторного webhook.

Второй эксперимент: останови только брокер, оплати, затем запусти брокер. Заказ сам не исправится — outbox ещё нет. Нажми «Сверить с провайдером»: событие будет опубликовано и обработано. Это демонстрация границы гарантии, а не повод скрыть ошибку автоматическим повтором в браузере.

Интеграционные тесты используют отдельный RabbitMQ на 5673/15673, случайный префикс на каждый прогон и удаляют только свои очереди. Dev-брокер не трогают. По умолчанию тесты сбоя перезапускают исключительно rabbitmq-test. При TEST_RABBITMQ_URL они пропускаются; для отдельного локального контейнера можно явно разрешить эти проверки через TEST_RABBITMQ_CONTAINER. Это разрешение остановить и запустить именно указанный контейнер, поэтому никогда не указывай dev-брокер или общий сервер.

Проверяются асинхронное обновление, стабильный eventId, перезапуск брокера, обработка при выключенных платежах, повторы, временная ошибка SQL, retry/DLQ, лимит повторов, mandatory return и окно без outbox. Непосредственные SQL-сбои создаются только в одноразовой тестовой базе; dev-таблицы не переименовываются.

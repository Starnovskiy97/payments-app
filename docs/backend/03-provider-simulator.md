# Этап 3: внешний провайдер и подписанные webhooks

> Разбор этапа интеграции с провайдером. В [следующем этапе](04-rabbitmq-delivery.md) внутренний HTTP-вызов заказов заменён RabbitMQ, а статус published означает подтверждение брокера, не обработку заказа. Сам внешний webhook остаётся HTTP.

## Разделение ответственности

```text
orders-service → payments-service → payment-provider-simulator
                       ▲                         │
                       └──── signed webhook ─────┘
```

Симулятор — самостоятельный NestJS-процесс на 3003 с собственной PostgreSQL на 15436. Он не читает наши таблицы. Наш сервис хранит связь с заказом, а провайдер — собственную внешнюю операцию и её результат.

При подключении реальной компании будем писать новый адаптер PaymentProvider, а не менять сервис заказов. Симулятор останется для локальных тестов. Его не следует публиковать в интернете или использовать для реальных денег.

## Запуск и переход

```bash
npm install
npm run db:up
npm run db:migrate
npm run dev
```

Миграция payments-service добавляет nullable-поля provider_payment_id и checkout_url. История не удаляется. Старые mock-платежи нельзя автоматически считать внешними операциями: для новых экспериментов создай новые заказы. У провайдера своя роль без superuser и свой volume.

## Два уровня идемпотентности

Клиент отправляет Idempotency-Key. Наш сервис сохраняет ключ и собственный UUID до внешнего HTTP-вызова. Этот UUID передаётся провайдеру как merchantPaymentId и служит там уникальным ключом. В ответ приходят другой UUID и checkoutUrl.

Поэтому таймаут не означает отказ: провайдер мог сохранить операцию и потерять ответ. Повтор с тем же нашим ID возвращает прежнюю внешнюю запись. На обеих сторонах проверяются сумма, валюта и метод. Пока внешний ID неизвестен, наша запись остаётся pending с пустой ссылкой — новую попытку создавать нельзя.

`src/providers/payment-provider.ts` задаёт интерфейс и DI-токен, `SimulatorPaymentProvider` реализует create/get через Axios. Внешний вызов выполняется после коммита локального намерения, без удержания SQL-блокировки. Для настоящего провайдера нужно использовать именно его протокол идемпотентности.

## Платёжная страница

Пользователь переходит по checkoutUrl на другой сервер. Страница — обычный HTML и Axios, без усложнения основного React-приложения. Браузер не получает API-токен и секрет webhook. Кнопка на этой странице меняет результат у симулятора, а не напрямую в payments-service.

Симулятор сохраняет финальный статус и eventId транзакционно, затем отправляет webhook. Повтор противоположного результата отклоняется. Тот же финальный результат можно отправить повторно, в том числе после рестарта.

## Подпись

```text
POST /webhooks/simulator
x-provider-timestamp: время в секундах
x-provider-signature: HMAC-SHA256(secret, timestamp + "." + rawBody)
```

В Nest включён rawBody. Guard проверяет формат подписи, возраст запроса (до пяти минут в обе стороны), затем сравнивает HMAC через timingSafeEqual. Подписываются исходные байты, а не JSON.stringify уже распарсенного объекта: пробелы и порядок полей влияют на подпись.

После проверки подписи и DTO сервис дополнительно читает факт через API провайдера. ID, сумма, валюта, метод и статус должны соответствовать нашей записи и уведомлению. checkoutUrl разрешён только с origin, заданного PROVIDER_PUBLIC_URL. API защищён отдельным PROVIDER_API_TOKEN.

Callback URL не принимается от клиента: PAYMENTS_WEBHOOK_URL фиксирован конфигурацией симулятора. Это не позволяет использовать создание платежа для произвольных HTTP-запросов к чужим адресам.

Схема HMAC учебная. В реальной интеграции обязательно следовать точному протоколу провайдера, включая формат подписи, смену секретов и повторы.

## Повторы — не новые оплаты

Отдельного inbox с дедупликацией eventId пока нет. Идемпотентность основана на неизменяемом финальном статусе платежа, транзакционной блокировке строки и безопасном обновлении заказа. Повтор может увеличить счётчик доставки, но не создаёт платёж заново. Поэтому счётчик не равен числу уникальных событий.

Существуют две независимые доставки:

- webhookStatus/webhookAttempts у провайдера — принят ли результат нашим payments-service;
- notificationStatus/notificationAttempts в платежах — получил ли результат orders-service.

Успех первой не означает успех второй. Недоступность заказов не отменяет оплату. HTTP выполняется вне транзакций: фиксация результата и сетевой вызов не атомарны. Автоматической фоновой доставки пока нет.

## Сверка

POST /payments/:id/sync читает фактическое состояние провайдера и обрабатывает финальный результат тем же путём, что webhook. Если внешний ID неизвестен, повторяет идемпотентное создание с нашим ID. GET платежа остаётся чтением локальной базы, без скрытых внешних запросов.

Сверка также повторяет уведомление заказов. Поэтому восстановление через исходный запрос оплаты может увеличить notificationAttempts. Провайдер и заказы не обязаны менять состояние одновременно; ручной повтор исправляет часть окон рассогласования, но не является outbox или распределённой транзакцией.

## Сбои для экспериментов

На странице провайдера можно:

- сохранить результат и потерять webhook;
- задержать webhook на две секунды после коммита;
- отправить 2–3 копии одного события;
- повторить финальный webhook.

В магазине «Следующее создание: потерять ответ» задерживает внешний ответ на 2,5 секунды при таймауте адаптера 1,5 секунды. Операция коммитится до задержки. После ошибки повтори исходный ключ: ID провайдера не изменится.

Одноразовая настройка задержки хранится в памяти и относится к следующему запросу любого клиента. Она не предназначена для одновременных экспериментов нескольких пользователей. Сами операции долговечны. После рестарта в любой момент можно повторить webhook или сверку, но автоматически они не запускаются.

## Проверки

20 интеграционных сценариев проходят через настоящий отдельный процесс симулятора. Проверяются миграции и откат, разные ID, перезапуск всех трёх приложений, отсутствие старого mock-result, подписи и их срок, точные байты с пробелами, проверка факта у провайдера, потеря webhook, задержки, дубликаты и таймаут после внешнего коммита.

Тесты используют три одноразовые базы на отдельных PostgreSQL, dev-данные не очищают. Симулятор в тестах слушает 3105. Далее — гарантированная доставка между нашими сервисами через RabbitMQ и outbox; внешний webhook останется HTTP-запросом.
